title: docspine-Prüfung statt eigenem Traceability-Gate
status: accepted

## Kontext

Mit ADR-0001 hat blocpress die Dokumentationsmethodik des Ursprungsprojekts übernommen,
einschließlich eines eigenen Traceability-Gates: Das Modul `blocpress-req-trace`
schrieb über einen JUnit-Listener die Ergebnisse von Tests mit `@Tag("REQ-…")` nach
`target/req-coverage.json`, und `blocpress-req-check` prüfte sie als letztes
Reactor-Modul gegen die Requirements. Der Code beider Module war eine Kopie aus dem
Ursprungsprojekt.

docspine stellt die Methodik und die Prüfung inzwischen als eigenes, versioniertes Paket
bereit. Die Prüfung liest JUnit-XML-Berichte und findet sie in allen Modulen selbst;
die Requirement-ID steht dabei im Testnamen.

## Entscheidung

blocpress nutzt die docspine-Prüfung statt eines eigenen Gates:

- Tests tragen die Requirement-ID im Anzeigenamen (`@DisplayName("REQ-…: …")`); Surefire
  schreibt Anzeigenamen von Klasse und Methode in die Berichte.
- Die Prüfung läuft als eigener Schritt direkt nach `mvn verify`, in der CI und im
  Release-Workflow ebenso wie lokal.
- `blocpress-req-trace` und `blocpress-req-check` entfallen.

Verworfen:
- **Eigenes Gate behalten:** doppelter Code zum Ursprungsprojekt, der auseinanderläuft.
- **docspine-Prüfung in einem Zusatzmodul als letztes im Reactor:** funktioniert, ist
  aber ein Modul ohne Code nur für einen Aufruf.
- **Prüfung von Hand:** lässt sich vergessen.

## Konsequenzen

- Ein lokales `mvn verify` allein prüft die Doku nicht; der zweite Befehl steht in
  `AGENTS.md`, die CI prüft in jedem Fall.
- Zum Bauen ist Python 3.9 oder neuer nötig.
- Ein Dokumentationsfehler lässt die CI scheitern, auch wenn der Code in Ordnung ist.
