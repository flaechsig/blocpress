Architecture overview

🌐
blocpress-studio

Port 8082 — browser portal, the only public entry; forwards to the Workbench

🛠
blocpress-workbench

Port 8081, internal — develop, test and approve templates; search via Elasticsearch

📑
blocpress-render

Port 8080 — Render API (ODT→PDF/RTF) for your applications

Deployment principle: Templates are developed in the Workbench (database workbench) and copied into the database production on approval (APPROVED). The Render API reads exclusively from production. Both services create and migrate their tables themselves on start (Liquibase) — you only provide the two empty databases.
1

Check prerequisites

  • A Kubernetes cluster with an ingress controller and a default storage class, about 4 CPU and 4 GiB free
  • kubectl 1.27 or newer (Kustomize is built in)
  • Internet access for pulling the images

No cluster at hand? k3d runs k3s in Docker and brings Traefik as ingress controller and a local storage class. This creates a cluster whose ingress is reachable on localhost:8088:

k3d cluster create blocpress -p "8088:80@loadbalancer" --wait
kubectl get nodes
2

Create namespace and database secret

The manifests install everything into the namespace blocpress and read the database credentials from the secret blocpress-db. Choose your own password:

kubectl create namespace blocpress
kubectl -n blocpress create secret generic blocpress-db \
  --from-literal=username=blocpress \
  --from-literal=password='your-secure-password'
Security: keep the password out of Git. In production, create the secret from your secret store (e.g. Sealed Secrets or External Secrets).
3

Install Blocpress

The manifests live in the repository under deploy/k8s. Apply them for a release tag:

kubectl apply -k "github.com/flaechsig/blocpress/deploy/k8s?ref=v2.8.0"
kubectl -n blocpress wait --for=condition=Available deployment --all --timeout=300s
PartContains
deploy/k8s/apprender, workbench, studio, Elasticsearch (single node)
deploy/k8s/postgresPostgreSQL 18 in the cluster; creates the databases workbench and production
deploy/k8sboth of the above plus an Ingress for the Studio at /
First start takes longer: the images are pulled once. render and workbench wait for the database, then create their tables (Liquibase) — watch it with kubectl -n blocpress get pods -w.

5

Approve your first template and render it

In the Studio, a template designer uploads an ODT template and submits it (status SUBMITTED). As a reviewer:

  1. Select the template and review the details
  2. Check the test data previews and run the regression test ("Run all")
  3. If there are concerns: "Reject" with a reason
  4. To approve: "Approve" → status changes to APPROVED

The same steps through the API, with the sample invoice template and its data:

STUDIO=http://localhost:8088
ID=$(curl -s -F name=invoice -F file=@invoice.odt $STUDIO/api/workbench/templates | jq -r .id)
curl -X POST $STUDIO/api/workbench/templates/$ID/submit
curl -X PUT -H "Content-Type: application/json" -d '{"newStatus":"APPROVED"}' \
  $STUDIO/api/workbench/templates/$ID/status
Automatic deploy: approval copies the template from the Workbench into the database production. It is immediately available under POST /api/render/{name} — no manual step required.

Render a template via API (after approval)

Name-based rendering 
# Authorization header only needed with BLOCPRESS_AUTH_ENABLED=true (step 6)
$ curl -X POST \
    http://localhost:8080/api/render/invoice \
    -H "Authorization: Bearer $JWT_TOKEN" \
    -H "Content-Type: application/json" \
    -d "{\"outputType\":\"pdf\",\"data\":$(cat invoice.json)}" \
    -o invoice.pdf

✓  invoice.pdf  (57 KB)  200 OK
6

Configure JWT authentication (optional)

JWT authentication of the Render API is off by default. When it is on, every endpoint below /api/render/ — rendering, jobs, dashboard — requires a valid Bearer token, otherwise HTTP 401. Blocpress validates the token with a public key (RS256); without a key the service refuses to start. Use the key of your Identity Provider (Keycloak, Okta, Azure AD, …) or generate a test key pair with openssl genrsa -out private.pem 2048 && openssl rsa -in private.pem -pubout -out public.pem. 

# the secret key becomes the environment variable of the same name
kubectl -n blocpress create secret generic blocpress-jwt \
  --from-file=MP_JWT_VERIFY_PUBLICKEY=public.pem
kubectl -n blocpress set env deploy/blocpress-render --from=secret/blocpress-jwt \
  BLOCPRESS_AUTH_ENABLED=true \
  MP_JWT_VERIFY_ISSUER=https://auth.example.com/realms/myrealm
kubectl -n blocpress rollout status deploy/blocpress-render
What stays open: the internal template import (/api/render/templates/import, called by the Workbench on approval) and /q/health. Never expose the Render API to the outside without blocking the import path. The Workbench does not validate tokens on the server side yet — protect the Studio via your network or ingress (e.g. OAuth2 proxy).

Production operation

Use your own PostgreSQL

Install only deploy/k8s/app and provide PostgreSQL 18 yourself: create the empty databases workbench and production owned by the user from the secret blocpress-db, and point the service name blocpress-db at your server. The services create their tables on start. 

# kustomization.yaml of your own overlay
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: blocpress
resources:
  - github.com/flaechsig/blocpress/deploy/k8s/app?ref=v2.8.0
  - db-service.yaml        # Service "blocpress-db" of type ExternalName → your DB host
  - ingress.yaml           # your ingress with TLS for blocpress-studio:8082

Apply updates

Change the ref to the new release tag and apply again. Schema changes are migrated automatically when the new pods start.

kubectl apply -k "github.com/flaechsig/blocpress/deploy/k8s?ref=vX.Y.Z"

Back up PostgreSQL data

for db in workbench production; do
  kubectl -n blocpress exec blocpress-db-0 -- pg_dump -U blocpress $db > ${db}_$(date +%Y%m%d).sql
done

Sizing and scaling

render is stateless: for more load add replicas instead of workers. Each pod uses as many LibreOffice workers as its CPU limit allows (standard size: 2 CPU, 640 MiB, ≈ 3.7 renders/s). Run a single Workbench instance. Details: render sizing guide. 

kubectl -n blocpress scale deploy/blocpress-render --replicas=3
